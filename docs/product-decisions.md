# Prototype implementation decisions

The PRD and subsequent user instructions define the framework. These are conservative implementation decisions, not assertions that the user individually approved every unresolved detail.

- All four modules are implemented; the original Coming Soon instructions are treated as intermediate development phases.
- The five detailed room records and five pending / three historical approvals take precedence over optional dashboard example numbers. Initial KPIs are 3 monitored buildings, 5 classrooms, 3 AC ON, 5 pending. The full map inventory is larger than the monitored inventory. Map footprints were manually transcribed from the supplied raster and should receive source-assisted geometry verification before any production use.
- `/rules-settings` is the fourth module. `/operating-rules` redirects to it. Approval `itemId` links open the appropriate pending modal or historical detail.
- The daily chart is scoped to the same five rooms. Scheduled counts derive from the confirmed schedules at each sample time. The separate illustrative HVAC time series has room-level membership and never exceeds the monitored population. Chart differences are not claimed to prove waste.
- The fixed room reference snapshot is 2026-11-17 at 13:15 Asia/Hong_Kong. Calendar dates and real action timestamps are distinct. Date-only arithmetic avoids browser timezone shifts.
- Successful Apply records a simulated plan and completes that workflow. It updates history, activity and approval counts, not current temperature, occupancy or HVAC sensor state. Saved overlapping plans receive a warning and remain separate; there is no schedule execution/merging engine.
- ON/OFF and date/time validation apply to every configuration. OFF has null mode/setpoint on persistence. Same-day windows only. Cooling, Dehumidify and Energy Saving are illustrative configurable modes; Heating is shown disabled because the HKU-focused MVP does not establish heating capability. No displayed mode claims actual room equipment support.
- Module 3 retains the PRD's 18–30°C / 0.5°C controls and the original 21.5°C comfort case. Targets outside the standard 23–26°C reference show a warning. General user-created cooling rules use 23–26°C. Administrator comments remain optional.
- Persistent approvals have only PENDING, COMPLETED and REJECTED. Configuring is temporary. Back to Review discards the provisional configuration and retains the optional comment. Review may close; Configuring cannot close by X/Escape/overlay; success/rejection requires an explicit return action. Reloading an unsubmitted configuration leaves the persisted item Pending.
- A final transaction saves decision, immutable request evidence, configuration, activity and timeline together. A failed local-storage write does not show success. Double processing is rejected. History is read-only and never recomputes evidence from current rooms.
- Rules use one primary and at most one AND condition. Drafts require only a valid unique name; activation validates the full form. Editing retains rule IDs. Saving an existing active rule as Draft pauses it. Drafts cannot bypass validation via a toggle.
- System rule parameters and statuses remain read-only. User-created rules support editing and Active/Inactive toggling. Disabling does not delete existing requests.
- No automatic evaluation is claimed. Occupancy percentages, arbitrary feedback windows and complex schedule conditions can be configured but are not inferred from inadequate binary/30-minute evidence. The reference RUL-002 drawer shows BOTH the 23.5°C pre-cooling phase and 24.5°C restoration phase; it does not falsely encode them as an executed single-stage command. APR-2026-005 is explicitly a distinct predefined pre-operation scenario rather than a fabricated RUL-002 trigger.
- The impact snapshot is a fixed four-opportunity scenario, independent of pending count or approvals. Electrical-input-power × avoidable-hour assumptions sum to 18.6 kWh/day; the illustrative factor 0.40 produces 7.4 kg CO₂e/day after rounding. The methodology modal exposes the inputs. These are not measured savings or an official emission factor.
- Map Reset keeps the currently selected building for map-origin directory sessions; sidebar Reset restores All Buildings. Clear all filters always removes the building restriction. Filters are encoded in the URL and preserved on room-detail return; the selected schedule date initializes the detail calendar week.
- Calendar date and previous/next-week actions switch weeks immediately. Refresh validates and applies the visible time range and re-reads local confirmed events. Event rendering clips to the visible range, preserves exact minutes and lays overlapping events side by side.
- The user's later HKU Portal style request supersedes the suggested teal primary accent. Branding uses an HKU crest plus school name, divider, Campus cooling Workbench label, and neutral administrator avatar. White/gray surfaces and green accents do not alter the original map image or business status semantics.

Remaining production concerns: authoritative brand assets/source verification; field-verified building geometry and labels; actual equipment capabilities; real occupancy/weather/feedback collection; backend security and authentication; schedule conflict resolution and execution; real outcome measurement. None is represented as implemented by this frontend prototype.
